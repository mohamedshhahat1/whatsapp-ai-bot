# Mobile Push Notifications (FCM / APNs)

Operators used to learn about new work only through the dashboard WebSocket,
which means only while an app was open and in the foreground. This feature
delivers notifications through Firebase Cloud Messaging on Android and APNs via
Firebase on iOS, so a phone in a pocket still buzzes.

Push is **off by default**. A deployment that has not completed the Firebase
setup below behaves exactly as before.

---

## 1. What triggers a notification

| Event | Notification | Type sent in `data` |
| --- | --- | --- |
| A new sales lead is tagged | "New Sales Lead" | `sales_lead` |
| The AI hands off to a person | "A Customer Needs a Person" | `handoff` |
| A conversation is assigned to an operator | "Conversation Assigned to You" | `assigned` |
| A customer messages while the conversation is in **human** mode | "New Customer Message" | `customer_message` |

Nothing else notifies. In particular: AI replies, an operator's own replies, a
handoff **back** to the AI, session close and session reopen are all silent.
Read receipts, delivery receipts and typing indicators never reach the event bus
at all.

An inbound customer message while the conversation is still in **bot** mode is
also silent -- the AI answers it within seconds, and it is nobody's outstanding
work.

## 2. Firebase setup

1. Create (or open) a project at <https://console.firebase.google.com>.
2. **Project settings -> General** and copy the **Project ID**. This is the
   value for `FCM_PROJECT_ID`. It is not the project *number*; the numeric one
   produces a 404 from the send endpoint.
3. **Project settings -> Service accounts -> Generate new private key**. This
   downloads a JSON file.
4. That file is the value of `FCM_CREDENTIALS`. **Never commit it.** It is a
   private key that can send notifications to every device in the project.
   `.gitignore` already covers `.env*`, but the JSON itself must be kept out of
   the repository too.

Preferred way to supply it in production, using the Docker secret mechanism this
project already has (see `docs/SECRETS.md`):

```bash
# on the deployment host
install -m 600 /dev/null ./secrets/fcm_credentials
cat firebase-service-account.json > ./secrets/fcm_credentials
```

Then either mount it as a Docker secret in `SECRETS_DIR`, or point at it:

```bash
FCM_CREDENTIALS_FILE=/run/secrets/fcm_credentials
```

Every secret backend the main configuration supports works here too: environment
variable, `<FIELD>_FILE`, Vault, Docker secret, and `.env` for development only.

## 3. Environment variables

| Variable | Default | Meaning |
| --- | --- | --- |
| `PUSH_ENABLED` | `false` | Master switch. Nothing is sent while this is false. |
| `FCM_PROJECT_ID` | *(empty)* | Firebase project **ID**. |
| `FCM_CREDENTIALS` | *(empty)* | Service-account JSON, verbatim. Secret. |
| `PUSH_DEFAULT_TITLE` | `New Customer Message` | Fallback notification title. |
| `PUSH_DEFAULT_BODY` | `You have a new customer message.` | The body shown to every `private` device. |
| `PUSH_ANDROID_CHANNEL` | `whatsapp_ai_bot_alerts` | Android channel id. **Must match `kAndroidChannelId` in the app.** |
| `PUSH_TIMEOUT_SECONDS` | `10` | Per-request timeout to FCM. |
| `PUSH_MAX_ATTEMPTS` | `3` | Reserved for the push retry policy. |
| `PUSH_BACKOFF_MAX_SECONDS` | `8` | Upper bound on retry backoff. |

If `PUSH_ENABLED=true` but the project id or credentials are missing, the
service reports itself unconfigured and sends nothing rather than failing per
notification.

Apply the migration after deploying:

```bash
docker compose exec app alembic upgrade head   # 0008_device_tokens
```

## 4. Android configuration

1. In the Firebase console add an **Android app** whose package name matches
   the one in `mobile/android/app/build.gradle.kts`.
2. Download `google-services.json` and place it at
   `mobile/android/app/google-services.json`.
3. `mobile/android/` is generated by `flutter create` and is **not tracked in
   this repository**, so the two edits below have to be made locally.

In `mobile/android/settings.gradle.kts`, add the Google services plugin:

```kotlin
plugins {
    id("com.google.gms.google-services") version "4.4.2" apply false
}
```

In `mobile/android/app/build.gradle.kts`:

```kotlin
plugins {
    id("com.android.application")
    id("kotlin-android")
    id("dev.flutter.flutter-gradle-plugin")
    id("com.google.gms.google-services")
}
```

**Core library desugaring** is required by `flutter_local_notifications`.
Without it the build fails at `:app:checkDebugAarMetadata`:

```kotlin
android {
    compileOptions {
        sourceCompatibility = JavaVersion.VERSION_11
        targetCompatibility = JavaVersion.VERSION_11
        isCoreLibraryDesugaringEnabled = true
    }
}

// outside the android { } block
dependencies {
    coreLibraryDesugaring("com.android.tools:desugar_jdk_libs:2.1.4")
}
```

Note the Kotlin DSL syntax: `isCoreLibraryDesugaringEnabled = true`, not the
Groovy `coreLibraryDesugaringEnabled true`.

Android 13+ asks the user for notification permission at runtime; the app
requests it on first launch.

## 5. iOS / APNs configuration

1. In the Firebase console add an **iOS app** with the app's bundle id.
2. Download `GoogleService-Info.plist` and add it to
   `mobile/ios/Runner/` **through Xcode**, so it is added to the target rather
   than merely sitting in the folder.
3. In the Apple developer portal create an **APNs authentication key** (`.p8`),
   and upload it under Firebase **Project settings -> Cloud Messaging -> Apple
   app configuration**, with its Key ID and your Team ID.
4. In Xcode, under **Signing & Capabilities**, add **Push Notifications** and
   enable **Background Modes -> Remote notifications**.
5. Push notifications do not work on the iOS simulator. Use a real device.

## 6. Payload and privacy

The notification body never contains customer content. What is sent:

```json
{
  "notification": { "title": "New Sales Lead", "body": "You have a new customer message." },
  "data": {
    "conversation_id": "1234",
    "notification_type": "sales_lead",
    "timestamp": "2026-08-04T21:12:00+00:00"
  }
}
```

Never included, anywhere: customer phone number, WhatsApp id, message text,
prices, or any other business detail. `data` carries exactly those three keys.

Each device chooses how much it shows, sent at registration as
`notification_privacy`:

- **`private`** (default) -- the lock screen shows
  "You have a new customer message."
- **`preview`** -- the lock screen may show the customer's **name** only.

The choice is stored per device, not per person, and the decision is applied
per device during fan-out: one operator on `preview` and another on `private`
receive genuinely different payloads for the same event. A `preview` device
falls back to the private wording when the customer has no display name.

## 7. Notification flow

```
inbound message / handoff / lead
        |
        v
events.publish()  ---> Redis pub/sub ---> dashboard WebSocket
        |
        v
push_dispatcher.dispatch()      decides whether this event deserves a push
        |                       (reads conversation.mode for inbound activity)
        v
NotificationService.notify()    audience, per-device privacy, metrics
        |
        v
FcmClient.send()  ---> FCM HTTP v1 ---> Android / APNs ---> device
```

Push hangs off the same choke point as the dashboard events, so any future code
path that announces a handoff gets notifications without further wiring.

On the device: a tap opens `/chats/<conversation_id>` directly. That works from
the background and from a cold start, where the launch message is replayed once
the widget tree exists.

## 8. Token lifecycle

- The app registers on every launch and on every token rotation. Registration
  is an upsert on the token, so a device is never duplicated.
- Re-registering a previously retired token re-enables it -- a reinstall, or a
  phone that was off long enough for Firebase to drop the token, comes back.
- A token Firebase rejects as `UNREGISTERED`, `INVALID_ARGUMENT` or
  `SENDER_ID_MISMATCH` is **soft-disabled**, not deleted.
- Transient failures (network, 429, 5xx) are retried with exponential backoff
  and jitter, and never retire a token.
- Offline devices need no handling here: FCM queues for them.

Endpoints, both under the existing admin surface and behind `X-API-Key`:

```http
POST /admin/device-token
{ "token": "...", "platform": "android", "notification_privacy": "private" }

DELETE /admin/device-token
{ "token": "..." }
```

`DELETE` answers 204 even for an unknown token, so the endpoint cannot be used
to discover which tokens are registered.

## 9. Metrics

| Metric | Type | Notes |
| --- | --- | --- |
| `push_sent_total{platform,type}` | counter | Accepted by Firebase. |
| `push_failed_total{platform,reason}` | counter | `transient`, `rejected`, `not_configured`. |
| `push_invalid_token_total{platform}` | counter | Tokens retired. A spike means a bad release or credential. |
| `push_delivery_latency_seconds` | histogram | FCM API round trip. |
| `registered_devices_total` | gauge | Enabled devices. Reading 0 means nobody can be notified. |

**`push_delivery_latency_seconds` does not measure delivery.** FCM returns when
it has *accepted* a message and issues no delivery receipt, so time-to-lock-screen
is not observable from the server. Do not build a delivery SLO on it. The name
keeps the spec's wording; the help text says the same thing.

## 10. Known limitations

**Notifications go to every registered device.** There is no `operators` table
in this system and no per-operator login -- authentication is a single shared
`ADMIN_API_KEY`, so the API can prove a request came from a trusted client but
not *which person* sent it. `device_tokens` therefore has no `operator_id`, and
"notify only the operator this conversation was assigned to" is not
implementable today. It becomes possible once real operator accounts exist, at
which point `device_tokens` gains an `operator_id` column.

A consequence worth knowing: anyone holding the admin key can register or
disable any device token.

**`notification_privacy` is per device, not per person**, for the same reason.

**Two of the section 11 test cases are manual.** Background notification and
notification-tap navigation are Flutter behaviours; `mobile/` has no test
directory and is not part of CI, so they are verified by hand:

1. Log in on a physical device, then background the app.
2. Trigger a handoff (send a message asking for a person).
3. The notification should appear on the lock screen showing only the default
   body.
4. Tap it -- the app should open that conversation directly.
5. Force-quit the app and repeat, to cover the cold-start path.

The server-side cases are automated in `tests/test_push_notifications.py`.

**Settings live in `app/core/push_config.py`**, not `app/config.py`. That is a
deliberate deviation from convention, taken because `config.py` can only be
rewritten whole by the tooling that added this feature and a previous whole-file
rewrite silently dropped a hundred lines of comments. Both classes read secrets
the same way, so nothing about operating them differs.
